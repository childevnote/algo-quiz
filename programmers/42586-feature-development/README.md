## 문제 분석 및 핵심 로직

각 기능은 진도 100%가 되어야 서비스에 반영(배포)할 수 있다. 기능별 현재 진도와 하루 개발 속도가 주어지며, 뒤쪽 기능이 먼저 완성되더라도 앞쪽 기능이 배포되기 전에는 함께 묶여서 배포된다. 배포는 하루에 한 번, 하루의 끝에 이루어진다. 각 배포 시점에 몇 개의 기능이 함께 배포되는지를 순서대로 구하는 문제다.

**핵심 조건:**

1. **배포는 하루에 한 번:** 배포일은 정수(일 단위)다. 남은 진도를 속도로 나눈 값을 **올림**해야 한다.
2. **순서 보장:** i번 기능보다 뒤에 있는 기능은 i번 기능의 배포일보다 먼저 배포될 수 없다. 먼저 완성됐으면 i번 기능이 배포될 때까지 대기한다.
3. **배포 그룹:** 앞쪽 기능의 배포일을 기준으로, 그 날짜를 넘지 않는 뒤쪽 기능들은 모두 같은 배포에 묶인다. 넘기는 기능부터 새 배포 그룹이 시작된다.

## 초심자 방식 vs 개선 방식

### 초심자 방식 1: 날짜를 하루씩 증가시키며 시뮬레이션

`day`를 1부터 증가시키고, 매일 모든 기능의 진도를 갱신하면서 배포 가능한지 확인한다. 직관적이지만 문제가 있다. 전체 일수가 커지면(예: 진도 1%, 속도 1 → 99일) 매일 O(n) 순회가 필요해 O(n × 총일수)가 된다. 입력 범위가 100개 이하라 통과는 되지만, 일수를 직접 계산하는 방법이 있는데도 시뮬레이션에 의존하면 습관으로 남기면 안 된다.

### 초심자 방식 2: 남은 일수는 계산했지만 배포 그룹을 이중 루프로

각 작업의 남은 일수 `days[i]`를 구한 뒤, 각 배포마다 "이 작업이 속할 배포를 찾기 위해" 앞쪽을 다시 훑는다. 앞 작업의 배포일보다 작은 날에 완성된 작업을 묶어야 하므로, 매번 앞쪽 구간을 다시 스캔하면 O(n²)이다.

### 개선 방식: 남은 일수 직접 계산 + 한 번의 순회로 그룹화

각 작업의 남은 일수는 시뮬레이션 없이 바로 계산된다. 진도 `p`, 속도 `s`일 때 `(100 - p) / s`를 올림하면 그 작업이 단독으로 배포 가능한 날이 나온다. (정수 연산으로는 `(100 - p + s - 1) / s`를 쓴다.)

```python
days = [math.ceil((100 - p) / s) for p, s in zip(progresses, speeds)]
```

그 뒤에는 앞쪽 작업의 배포일(현재 그룹의 기준일) 하나만 기억하면 된다. 앞에서 뒤로 훑으면서:

- `days[i] <= 기준일` → 먼저 완성됐거나 같은 날이므로 현재 배포에 합류
- `days[i] > 기준일` → 새 배포 그룹 시작, 기준일을 `days[i]`로 갱신

```python
cur_day, count = days[0], 1
for d in days[1:]:
    if d <= cur_day:
        count += 1
    else:
        answer.append(count)
        cur_day, count = d, 1
```

이 한 번의 순회가 순서 보장을 자동으로 처리하는 이유: 기준일은 "지금까지 본 작업 중 가장 늦게 배포된 날"과 같다. 뒤쪽 작업이 그 날짜를 넘지 않으면 어떤 경우에도 앞쪽 작업보다 먼저 나갈 수 없으므로 같은 그룹에 속하고, 넘으면 앞쪽 작업이 모두 나간 뒤에 나가므로 새 그룹이 된다.

### 주의할 점 (자동 풀이 과정에서 확인)

- 올림을 빼먹고 내림으로 계산하면 배포일이 하루씩 앞당겨져 답이 어긋난다. 정수 연산 `(100 - p + s - 1) // s`를 쓰면 부동소수점 오차를 피할 수 있다.
- 마지막 그룹은 루프가 끝나고 나서 추가해야 한다. 루프 안의 `else`에서만 `append`하면 마지막 그룹이 누락된다.

## 최종 솔루션 코드

```python
import math

def solution(progresses, speeds):
    # 1. 각 작업이 완성되기까지 남은 일수 계산 (올림)
    days = [math.ceil((100 - p) / s) for p, s in zip(progresses, speeds)]
    # 2. 앞 작업의 배포일을 넘지 못하면 함께 배포, 넘으면 새 배포
    answer = []
    cur_day, count = days[0], 1
    for d in days[1:]:
        if d <= cur_day:
            count += 1
        else:
            answer.append(count)
            cur_day, count = d, 1
    answer.append(count)
    return answer
```

```java
class Solution {
    public int[] solution(int[] progresses, int[] speeds) {
        int n = progresses.length;
        // 1. 각 작업이 완성되기까지 남은 일수 계산 (올림)
        int[] days = new int[n];
        for (int i = 0; i < n; i++) {
            days[i] = (100 - progresses[i] + speeds[i] - 1) / speeds[i];
        }
        // 2. 앞 작업의 배포일을 넘지 못하면 함께 배포, 넘으면 새 배포
        java.util.List<Integer> list = new java.util.ArrayList<>();
        int curDay = days[0], count = 1;
        for (int i = 1; i < n; i++) {
            if (days[i] <= curDay) {
                count++;
            } else {
                list.add(count);
                curDay = days[i];
                count = 1;
            }
        }
        list.add(count);
        return list.stream().mapToInt(Integer::intValue).toArray();
    }
}
```

로컬 측정 결과:

| 언어 | 예제 케이스 평균 | n=100,000 무작위 | 메모리(피크) |
|---|---|---|---|
| Python | 2.15 µs | 77.0 ms | 1.53 MiB |

- 시간복잡도: **O(n)** — 남은 일수 계산 1회 + 그룹화 순회 1회
- 공간복잡도: **O(n)** — `days` 배열. days 배열 없이 스트리밍으로 계산하면 O(1) 추가 공간으로 줄일 수 있으나, 가독성을 위해 배열을 유지했다.

## 요약

1. 각 작업의 남은 일수는 시뮬레이션 없이 올림 나눗셈으로 직접 계산한다.
2. 앞쪽 작업의 배포일(누적 기준일)을 하나만 유지하면서 한 번 훑으면 배포 그룹이 나뉜다.
3. 올림 누락과 마지막 그룹 누락이 이 문제의 대표적인 실수 지점이다.
