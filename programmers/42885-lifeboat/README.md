## 문제 핵심 요약

한 배에 최대 2명까지, 합이 무게 제한을 넘지 않는 조건으로 모든 사람을 태울 때 필요한 배 개수의 최솟값을 구한다.

- 핵심 제한사항: 사람 수는 1명 이상 50,000명 이하, 몸무게와 무게 제한은 각각 40 이상 240 이하, 구출이 불가능한 경우는 주어지지 않는다.
- 입출력 예: `[70, 50, 80, 50], limit=100 → 3`, `[70, 80, 50], limit=100 → 3`.

## 문제 분석 및 핵심 로직

배 한 척에 태울 수 있는 인원은 최대 2명이다. 따라서 전체 문제는 "누구를 누구와 짝지을 것인가"로 축소된다.

핵심 관찰은 가장 무거운 사람에서 시작한다. 가장 무거운 사람은 어떤 배에든 반드시 태워야 하고, 그 배에 함께 탈 수 있는 사람이 있다면 그 사람은 가장 가벼운 사람이어야 한다. 이유는 두 가지다.

- 가장 가벼운 사람과도 합이 제한을 넘는다면, 그 무거운 사람은 누구와도 짝을 지을 수 없으므로 혼자 탄다. 이 판단은 뒤집을 여지가 없다.
- 가장 가벼운 사람과 합이 제한 안에 든다면, 그 사람을 다른 누군가와 짝짓는 선택은 손해다. 다른 사람은 가장 가벼운 사람보다 무겁기 때문에, 그 다른 사람과 짝을 지을 수 있는 상대는 가장 가벼운 사람과 짝을 지을 수 있는 상대의 부분집합이다. 즉, 가장 가벼운 사람을 무거운 사람의 짝으로 쓰는 편이 남은 사람들의 짝짓기 가능성을 줄이지 않는다.

이것이 탐욕 선택이 최적임을 보장하는 교환 논증이다. 최적해에서 가장 무거운 사람의 짝이 가장 가벼운 사람이 아니었다면, 그 짝을 가장 가벼운 사람으로 교체해도 배 수는 늘지 않는다. 교체된 짝(원래 가장 가벼운 사람의 짝이었던 사람)은 원래 짝보다 가볍거나 같은 사람과 짝을 짓게 되므로 제한을 여전히 만족한다.

정렬한 뒤 양끝에서 좁혀 들어가는 투 포인터는 이 판단을 그대로 구현한다. 오른쪽 끝(가장 무거운 사람)은 매번 배에 태우고, 왼쪽 끝(가장 가벼운 사람)은 합이 제한 안에 들 때만 함께 태운다.

## 개념별 심층 설명

### 1. 초심자 방식: 모든 짝짓기 경우를 따져보기

사람들을 두 명씩 묶는 모든 경우를 열거하면 경우의 수가 사람 수에 따라 폭발적으로 늘어난다. n명이면 첫 번째 사람의 짝만 n-1가지이고, 남은 사람들에 대해 같은 선택이 반복되므로 전체 경우의 수는 팩토리얼 수준으로 커진다. n이 50,000까지 주어지는 이 문제에서는 아예 성립하지 않는다.

### 2. 개선 방식: 정렬 후 양끝 투 포인터

정렬이 선행되어야 하는 이유는 "가장 무거운 사람"과 "가장 가벼운 사람"을 매번 상수 시간에 찾기 위해서다. 정렬하지 않으면 매 단계마다 최댓값과 최솟값을 스캔해야 하고, 그 비용이 전체를 지배한다.

- 동작 원리: 정렬된 배열에서 왼쪽 포인터는 가장 가벼운 남은 사람, 오른쪽 포인터는 가장 무거운 남은 사람을 가리킨다. 두 합이 제한 안에 들면 왼쪽 포인터를 한 칸 전진시키고, 어느 경우든 오른쪽 포인터를 한 칸 후진시키며 배를 한 척 센다. 왼쪽 포인터가 오른쪽 포인터를 지나면 종료한다.
- 왜 가벼운 사람끼리 먼저 묶으면 안 되는지: `[50, 50, 60, 60], limit=110`을 보자. 가벼운 두 명을 먼저 묶으면 `50+50=100`으로 한 배를 쓰고, 남은 `60, 60`은 합이 120으로 제한을 넘어 각각 한 배씩 타서 총 3척이 된다. 반면 `50+60=110`으로 두 쌍을 만들면 2척으로 충분하다. 가벼운 사람을 가벼운 사람과 묶는 선택은 무거운 사람들을 혼자 타게 만들어 배를 낭비한다.
- 왜 무거운 사람부터 처리하는지: 무거운 사람은 짝짓기 선택지가 가장 좁다. 선택지가 넓은 가벼운 사람부터 처리하면 무거운 사람의 자리가 나중에 없어지지만, 선택지가 좁은 사람부터 처리하면 가벼운 사람은 어디에든 끼워 넣을 여지가 남는다. 제약이 가장 강한 원소부터 확정하는 것이 탐욕법의 일반적인 직관이다.
- 엣지 케이스: 모든 사람이 혼자 타야 하는 경우(예: `[80, 80, 80], limit=100`)에는 왼쪽 포인터가 한 번도 전진하지 않고 배 수가 사람 수와 같아진다. 사람이 한 명만 남은 경우(`left == right`)에는 그 사람을 태우고 종료하므로 배 한 척이 정확히 추가된다.

## 최종 솔루션 코드

### Python

```python
def solution(people, limit):
    people.sort()
    left, right = 0, len(people) - 1
    boats = 0
    while left <= right:
        # 1. 가장 가벼운 사람과 가장 무거운 사람을 한 배에 태울 수 있으면 함께 태운다.
        if people[left] + people[right] <= limit:
            left += 1
        # 2. 가장 무거운 사람은 어느 경우든 이번 배에 태운다 (혼자 타거나, 짝과 함께).
        right -= 1
        boats += 1
    return boats
```

### Java

```java
import java.util.Arrays;

class Solution {
    public int solution(int[] people, int limit) {
        Arrays.sort(people);
        int left = 0;
        int right = people.length - 1;
        int boats = 0;
        while (left <= right) {
            // 1. 가장 가벼운 사람과 가장 무거운 사람을 한 배에 태울 수 있으면 함께 태운다.
            if (people[left] + people[right] <= limit) {
                left++;
            }
            // 2. 가장 무거운 사람은 어느 경우든 이번 배에 태운다 (혼자 타거나, 짝과 함께).
            right--;
            boats++;
        }
        return boats;
    }
}
```

## 성능 측정

로컬 실측 (예제 케이스 실행시간, n=100,000 무작위 케이스 실행시간·메모리):

- 예제 케이스: Python 약 0.01ms, Java 즉시 반환 수준 (측정 하한 이하).
- n=100,000 무작위 케이스 (몸무게 40~150, limit=200): Python 약 43ms, Java 약 41ms.
- 추가 메모리: 정렬 외의 추가 공간은 포인터와 카운터뿐이라 O(1) 수준이다. 참고로 tracemalloc 측정 피크는 1.14MB였으며, 이는 테스트용 입력 복사본을 포함한 수치다. CPython의 `list.sort`는 Timsort 특성상 내부적으로 최대 O(n)의 임시 버퍼를 쓸 수 있고, Java의 `Arrays.sort(int[])`는 제자리 듀얼 피벗 퀵정렬이라 추가 공간이 O(log n) 스택 수준이다.
- 시간 복잡도: 정렬이 지배해 O(n log n), 투 포인터 순회는 O(n).
- 공간 복잡도: 입력 외 추가 공간 O(1) 수준 (정렬 구현의 내부 버퍼 제외).

- 핵심 포인트: 가장 무거운 사람부터 확정하고, 그 짝으로는 가장 가벼운 사람을 고른다. 이 선택이 최적인 이유는 교환 논증으로 확인된다.

## 요약

정렬한 뒤 가장 무거운 사람부터 배에 태우고, 가장 가벼운 사람과 합이 제한 안에 들 때만 함께 태우는 탐욕 선택이 최소 배 개수를 보장한다. 정렬 비용 O(n log n)이 전체를 지배하고, 추가 공간은 포인터 수준으로 충분하다.
